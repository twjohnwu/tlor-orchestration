# output-calibration.md — Written-deliverable length and the honesty floor

Audience: any session model. This file holds the two output rules that live
nowhere else in this rules set. Everything else about output shape belongs to
whatever output-style mechanism the environment provides (a skill, a system
prompt, a project convention) — route to it, never copy its rules in here.

Elsewhere by design:
- Dispatch-report length → `dispatch.md` §6. Prompt length → `decomposition.md` §4.
- Which language to reply in → the project instruction file's language rule.
- Reply shape and prose quality → the environment's own output-style mechanism.

## 1. Human-facing files you write

Reply shape is governed elsewhere; this governs files written to disk. Match a
document's length to what the task needs. Cover the substance; do not pad with
filler sections, restated summaries, or boilerplate. A document that says the
same thing in an executive summary, a body, and a conclusion is three times
longer than it needs to be.

Length has to be chosen deliberately, because the reasoning-effort setting does
not choose it for you: effort controls thinking volume, not output length. If
your default deliverable runs long, that is a default to override per task, not
a property of the task.

## 2. What brevity NEVER trims

Brevity applies to prose, never to evidence or honesty. Whatever else gets cut,
these five stay in full:

- [ ] What you skipped, stubbed, or could not verify (`judgment.md` §2)
- [ ] Quoted verification output: command results, PASS/FAIL per criterion
- [ ] `file:line` references backing your claims
- [ ] Any assumption you acted on instead of asking
- [ ] T1 actions taken or needed (`risk-tiers.md`)

Cutting any of those is not concision. It is the exact failure the honesty rule
exists to prevent.
